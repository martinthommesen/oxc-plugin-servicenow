None. This is a published npm library plus its build, documentation, and release tooling. There is no server, no client application, and no long-running process.

## Deployment model

Publication to the public npm registry from a tag-triggered GitHub Actions workflow using trusted publishing and provenance, split across six jobs with per-job permissions. Five workflows exist: continuous integration, release, governance audit, release-tag creation, and release recovery.

Not applicable: there is no database, ORM, migration directory, cache, queue, or durable state. Searches for persistence APIs, schema files, and migration tooling across `src/`, `scripts/`, and `.github/` returned only JSON data files that are committed source, not runtime state. `src/` contains zero `node:` imports, so the published plugin cannot perform input or output of its own.

# 4. Architecture and Data-Flow Map

## Component relationships

`src/index.ts` composes the plugin from `src/rules/index.ts`, which derives the registry from `ruleImplementations` in the catalog assembler. The catalog is now split: `src/catalog.ts` assembles fifty per-rule descriptor modules under `src/catalog/`. Presets in `src/configs/maps.ts` derive from `rulePlacements`. Rules call `beginRuleFile`, which returns the shared per-file analysis built by `src/analysis/file-analysis.ts`. That module composes scope information from `src/analysis/bindings.ts`, script context from `src/context/resolve.ts`, capability views from `src/glide/manifest.ts` and `src/fluent/registry.ts`, and object provenance from `src/analysis/path-state.ts`.

## Responsibility boundaries

Knowledge tables (`src/engine/features.ts`, `src/glide/manifest.ts`, `src/fluent/manifest.ts`) are separated from the analyzers that consume them, and both are separated from the rules that report. The separation holds; the remaining analyzer concern is traversal shape inside the analysis layer (PER-005), not a boundary violation.

## Dependency direction

Rules depend on analysis, analysis depends on knowledge tables and utilities, and nothing depends on rules except the catalog. A cycle check over all 183 `src/` modules during this review found zero import cycles. `src/index.ts` mutates `plugin.configs` after construction to break a value-level cycle between the plugin object and the configuration objects that embed it.

## Data ownership

`src/analysis/file-analysis.ts` owns the per-file analysis cache, keyed on the host `SourceCode` object in a `WeakMap` and then on filename, physical filename, working directory, a settings fingerprint, and a resolver version. `src/glide/manifest.ts` owns a small module-level capability cache bounded by scope and release. `src/fluent/registry.ts` now builds manifests lazily into a `Map` cache on first request per SDK version, replacing the previous eager construction of all 27 manifests at module load.

## Trust and privilege boundaries

Untrusted source AST enters through the host. Untrusted configuration enters through `context.settings` and `context.options` and is validated and deep-frozen before any rule reads it (POS-005). In CI the `workflow` job runs `npm ci --ignore-scripts` before the pin check, so dependency install scripts cannot run before the check, but a compromised `yaml` package could alter pin parsing itself; the `publish` job holds only `id-token: write` and never checks out the repository.

## Critical request paths

For each linted file: settings validation, context resolution, one shared analysis pass, then per-rule visitors. Rule `before()` hooks gate on context and return `false` to skip the file. Per-file state is now reset or computed per hook call, and a multi-file lifecycle test pins the behavior.

## Async workflows and actual delivery guarantees

Not applicable inside the plugin: analysis is fully synchronous, and `src/` contains no timers, workers, promises, or concurrency primitives. In the release pipeline the publish step is modelled with four explicit outcomes and treated as effectively once through registry verification as arbiter, which is the correct shape for a non-idempotent external side effect.

## Persistence and transaction boundaries

Not applicable: no persistence and no transactions exist. The only durable side effect in the whole system is npm publication, which is guarded by digest, provenance, and version-order checks.

## Cache ownership and invalidation

Four caches. The analysis cache is invalidated by identity of the host `SourceCode` plus a settings fingerprint. The settings memo is a `WeakMap` keyed on the raw settings object with a structural fingerprint guard. The Glide capability cache is keyed on scope and release and is bounded at three entries. The Fluent registry cache is keyed on SDK version and is bounded by the 27 supported versions.

## External dependencies

One runtime dependency, `@oxlint/plugins`. Four optional peers. Development dependencies include the sigstore verification stack used only by release scripts, and a pinned `yaml` package used only by the workflow pin check.

## Operational control points

The five workflows, the eleven required status checks named in `scripts/release-governance.json`, and the nightly governance audit. The governance audit fails closed on absent rulesets, the compatibility-matrix check runs in the test job, and a new schedule-only advisory job re-resolves the top of each declared peer range without gating.

## Compatibility boundaries

The export map, the preset maps, the ten flat configurations, `ServiceNowSettings`, rule names, message identifiers, and the `oxfmt.recommended.json` preset. The declared peer ranges now match the tested matrix cells exactly, with in-range patch drift covered advisorily rather than in gating CI.
