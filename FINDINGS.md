## Overall codebase health

This is a mature, unusually well-engineered repository. The rule catalog is a genuine single source of truth, options are single-sourced into schema and documentation, release provenance verification is stronger than most published packages, and the path-sensitive analyzer degrades under a deterministic budget instead of hanging. Every one of the eleven defects raised by the previous review round was fixed, and nine of them are verified closed here.

The remaining risk has moved. It is no longer concentrated in the analyzer internals that the last round repaired; it now sits in three places that the repository's own test harness structurally cannot see. First, the test harness constructs each rule once per assertion, so rule state that must reset per file is never exercised across files (COR-011). Second, the harness feeds small fixtures, so the analyzer's fixed work budget is never approached at realistic file sizes (PER-003). Third, the catalog's declared applicability is documentation rather than a checked contract, so a rule can ship with no context gate while its generated page states one (COR-015). One rule aborts the lint run outright on a legal input (COR-010).

A separate, non-code concern frames everything else. This branch is 142 commits ahead of and 40 commits behind `origin/main`, and `origin/main` already carries the released `v2.0.0` tag, a further ServiceNow release family, and the deletion of the plan documents this branch still lists as outstanding (DOC-003).

## Most serious risks

- COR-010: a self-referential constant alias makes `no-at-method` recurse until the stack overflows, throwing out of the rule and aborting the lint run.
- COR-011: two error-level rules keep a `reported` offset set in `createOnce` that `before()` never clears, so the second and later files with a violation at the same byte offset are silently clean.
- PER-003: the shared path-analysis budget is exhausted by an ordinary 300-line script, after which findings are silently dropped and the count stops growing with file size.
- SEC-001: the release-governance audit copies the desired configuration into the observed configuration when a ruleset is absent, so deleting or renaming the rulesets that enforce tag immutability and required checks reports green.

## Most important architectural concern

COR-015. The catalog declares each rule's authoring form, surfaces, and JavaScript modes, and that declaration drives the generated documentation and the preset placements, but nothing verifies it against the gate the rule actually implements. Two rules ship with no gate at all, and three rule pages state a mode restriction the engine deliberately does not apply. The catalog is otherwise the strongest structural idea in the repository (POS-003); the gap is that applicability is the one catalog field that is never checked.

## Most valuable simplification

REM-002. About 18,000 lines of one-off PR-51 remediation apparatus remain wired into validation, and DOC-003 shows the plan documents inside it now instruct a reader to redo work that `origin/main` has already shipped.

## Most valuable alternative implementation

IMP-001. The dependency-free `uses:` matcher is reopened rather than resolved. The hardening landed, but five legal YAML spellings of `uses:` still return no references, so the pre-install pin check can be bypassed by a workflow edit.

## Most valuable feature addition

DOC-005. The single highest-value addition is user-facing guidance for a quiet lint run. The architecture is deliberately silent in three distinct ways, and no document tells a user why or how to resolve it.

## Strongest feature-removal or consolidation candidate

REM-002, with REM-001 close behind. Neither can complete until this branch merges.

## Most important positive pattern to preserve

# 2. Repository and System Overview

## Repository structure

460 tracked files. `src/` holds 104 TypeScript files, `tests/` 147 files, `scripts/` 39 files, `docs/` 59 files, `examples/` 63 files, `plans/` 18 files, and `.github/` 14 files. Handwritten `src/` is about 13,500 lines; a further 16,025 lines are the generated `src/fluent/declaration-snapshots.ts`. `tests/` is about 11,300 lines and `scripts/` about 5,800.

## Languages and frameworks

TypeScript throughout `src/` and `tests/`, compiled by `tsc` with `strict`, `noUncheckedIndexedAccess`, `isolatedModules`, and `verbatimModuleSyntax`. Build scripts are plain ESM JavaScript (`.mjs`) with hand-written `.d.mts` declarations. The plugin targets the `@oxlint/plugins` API and is wrapped by `eslintCompatPlugin` for ESLint 9 and later.

## Applications and services

None. This is a published npm library plus its build, documentation, and release tooling. There is no server, no client application, and no long-running process.

## Deployment model

Publication to the public npm registry from a tag-triggered GitHub Actions workflow using trusted publishing and provenance, split across six jobs with per-job permissions.

## Data stores

Not applicable: there is no database, ORM, migration directory, cache, queue, or durable state. Searches for persistence APIs, schema files, and migration tooling across `src/`, `scripts/`, and `.github/` returned only JSON data files that are committed source, not runtime state.

## Integrations

The npm registry and the GitHub API, both reached only from `scripts/` during release and governance auditing. The linted ServiceNow source is read through the host's AST; the plugin never performs input or output of its own.

## Entry points

Package exports `.`, `./analysis`, `./oxfmt`, `./oxfmt.recommended.json`, and `./package.json`. Developer entry points are the 29 `package.json` scripts. Operational entry points are the three GitHub Actions workflows.

## Trust boundaries

Three. The linted source text and AST are untrusted input. The `settings.servicenow` object and rule options come from a repository-controlled lint configuration and are untrusted. The build and release scripts consume workflow inputs, tag names, registry responses, and sigstore bundles, all untrusted.

## Critical workflows

Resolve script context from settings and filename, build one shared per-file analysis, run rules against it, and report. Separately, verify workflow pins, validate the compatibility matrix, pack, publish with provenance, and verify the published artifact.

## Public contracts

The five export-map entries, the exported preset maps and flat configurations, the `ServiceNowSettings` shape, and the rule names and message identifiers.

## Persisted-data contracts

Not applicable: the package writes no persistent data. The committed JSON fixtures under `tests/fixtures/` and `scripts/` are compared, not migrated.

## Generated and vendored boundaries

`src/fluent/declaration-snapshots.ts` is generated by `scripts/audit-fluent-sdk.mjs` and carries a do-not-edit banner. `src/version.ts` is generated by `scripts/generate-version.mjs`. `docs/rules/**`, parts of `README.md`, `docs/compatibility.md`, and 13 example and fixture `.oxlintrc.json` files are generated from the catalog. No vendored third-party source is present in the tracked tree.

## Review-relevant worktree state

Clean at review time. The branch is 142 ahead of and 40 behind `origin/main`; the merge base is `682d906219e73c1c3f46ce7b0a632b3b10763714`. Tag `v2.0.0` resolves to `497f9d976f10a81d6e1ad6da7ccfe0294d832c2b` and is an ancestor of `origin/main` but not of this branch. See DOC-003.

# 4. Architecture and Data-Flow Map

## Component relationships

`src/index.ts` composes the plugin from `src/rules/index.ts`, which is derived from `src/catalog.ts`. Presets in `src/configs/` are derived from catalog placements. Rules call `beginRuleFile`, which returns the shared per-file analysis built by `src/analysis/file-analysis.ts`. That module composes scope information from `src/analysis/bindings.ts`, script context from `src/context/resolve.ts`, capability views from `src/glide/manifest.ts` and `src/fluent/registry.ts`, and object provenance from `src/analysis/path-state.ts`.

## Responsibility boundaries

Knowledge tables (`src/engine/features.ts`, `src/glide/manifest.ts`, `src/fluent/manifest.ts`) are separated from the analyzers that consume them, and both are separated from the rules that report. The separation holds well; COR-012 is a defect inside one knowledge table, not a boundary violation.

## Dependency direction

Rules depend on analysis, analysis depends on knowledge tables and utilities, and nothing depends on rules except the catalog. No cycles were found among `src/` modules. `src/index.ts` mutates `plugin.configs` after construction to break a value-level cycle between the plugin object and the configuration objects that embed it.

## Data ownership

`src/analysis/file-analysis.ts` owns the per-file analysis cache, keyed on the host `SourceCode` object in a `WeakMap` and then on filename, physical filename, working directory, a settings fingerprint, and a resolver version. `src/glide/manifest.ts` owns a small module-level capability cache bounded by scope and release. `src/fluent/registry.ts` builds all 27 manifests eagerly at module load.

## Trust and privilege boundaries

Untrusted source AST enters through the host. Untrusted configuration enters through `context.settings` and `context.options` and is validated and deep-frozen before any rule reads it (POS-005). In CI, the `workflow` job runs the pin check before `npm ci`, so a compromised dependency cannot disable it; the `publish` job holds only `id-token: write` and never checks out the repository.

## Critical request paths

For each linted file: settings validation, context resolution, one shared analysis pass, then per-rule visitors. Rule `before()` hooks gate on context and return `false` to skip the file. COR-011 shows this path carries state that outlives the file.

## Async workflows and actual delivery guarantees

Not applicable inside the plugin: analysis is fully synchronous. In the release pipeline the publish step is modelled with four explicit outcomes and treated as effectively once through registry verification as arbiter, which is the correct shape for a non-idempotent external side effect.

## Persistence and transaction boundaries

Not applicable: no persistence and no transactions exist. The only durable side effect in the whole system is npm publication, which is guarded by digest, provenance, and version-order checks.

## Cache ownership and invalidation

Three caches, all correct in ownership. The analysis cache is invalidated by identity of the host `SourceCode` plus a settings fingerprint. The settings memo is a `WeakMap` keyed on the raw settings object with a structural fingerprint guard. The Glide capability cache is keyed on scope and release and is bounded at three entries.

## External dependencies

One runtime dependency, `@oxlint/plugins`. Four optional peers. Development dependencies include the sigstore verification stack used only by release scripts.

## Operational control points

The three workflows, the twelve required status checks named in `scripts/release-governance.json`, and the nightly governance audit. SEC-001 and OPS-009 both weaken this layer.

## Compatibility boundaries

The export map, the preset maps, `ServiceNowSettings`, rule names, message identifiers, and the `oxfmt.recommended.json` preset. The declared peer ranges are broader than the tested matrix (OPS-011).

## [COR-010] A self-referential constant alias makes `no-at-method` recurse until the stack overflows

Record type: Defect or risk
ID category: COR
Primary component: Engine feature rule alias resolution
Identity statement: Constant alias resolution recurses without a visited set, so a self-referential or mutually referential binding never terminates
Fingerprint: sha256:281328e44f5400f01c6fcb97dd6bf49df4474c3bc02f1c9dbe5e5351b198f361
Status: Active

Classification: Confirmed defect
Severity or priority: High
Confidence: Confirmed
Affected components: `no-at-method` rule, the `classicEs5` preset, and every consumer linting classic JavaScript in Compatibility or ES5 mode

Evidence:
- `src/rules/no-at-method.ts:9-21`: `isBuiltInAtReceiver` resolves an identifier to its binding and, when the binding is a `const` `VariableDeclarator`, calls itself on that declarator's `init`. There is no visited set and no depth cap.
- Reproduction through the repository's own harness, file `src/server/test.js`, `settings.servicenow.javascriptMode` set to `es5`, source `const a = a;` followed by `a.at(0);` throws `RangeError: Maximum call stack size exceeded` out of the rule. The mutual form `const a = b;` `const b = a;` `a.at(0);` throws identically. The control `const a = [1];` `a.at(0);` correctly reports one diagnostic.
- `src/analysis/now-id.ts:70-84` and `src/analysis/fluent-imports.ts:225` show the visited-set discipline the codebase already applies to the same shape of walk.

Current behavior:
The rule throws an uncaught `RangeError` out of its `MemberExpression` visitor.

Expected or preferred behavior:
An alias cycle should terminate the walk and answer "not a built-in receiver", the same conservative answer the rule gives for any unresolved receiver.

Trigger or scenario:
A classic JavaScript file linted with `javascriptMode` `es5` or `compatibility` that contains a `const` binding whose initializer resolves back to itself, directly or through a chain, and a `.at(` member call on that binding.

Impact:
An unhandled exception from a rule is the most severe user-facing failure this product can produce. Under the ESLint command-line interface an uncaught rule error aborts the run, so one such line anywhere in a repository can stop the whole lint. The input is legal, parseable source; a linter is expected to survive it.

Reach:
Every consumer of the `classicEs5` preset, which sets `javascriptMode` to `es5`, and every consumer who sets that mode explicitly. The trigger is narrow, but once present it blocks the entire run rather than one file.

Root cause:
The recursive alias resolution added to make the rule see through constant aliases has no cycle guard, unlike the three other recursive resolvers in the codebase.

Why existing tests did not catch it:
`tests/rules/glide-and-engine.test.ts:136-171` covers array receivers, string receivers, and a single-hop constant alias. No test constructs an alias cycle. `docs/rules/no-at-method.md` records no false positives or known limitations for this path.

Minimal reproduction:
Lint `const a = a;\na.at(0);` as `src/server/test.js` with `settings.servicenow.javascriptMode` set to `es5`.

Recommended action:
Thread a `seen` set of binding identifiers through `isBuiltInAtReceiver` and return `false` when a binding is revisited.

Alternative approaches:
1. Add a fixed recursion depth cap. Simpler, but it silently truncates long legitimate alias chains and still costs the full depth on every call.
2. Resolve aliases iteratively with an explicit stack. Equivalent safety, larger diff, no added benefit here.
3. Keep current behavior. Not applicable: the current behavior is an uncaught exception on legal input.

Preferred option:
The visited set. It matches the pattern already used at `src/analysis/now-id.ts:70-84`, is a three-line change, and cannot truncate a legitimate chain. Confidence is Confirmed. No prerequisites. Evidence that would change it is proof that the host isolates rule exceptions per file, which would lower severity but not the need for the fix.

Implementation outline:
Change the signature of `isBuiltInAtReceiver` to accept a `Set<number>` of binding identifiers, add the resolved binding identifier before recursing, and return `false` when the identifier is already present. No caller outside the module.

Compatibility and migration: Not applicable: the change is internal to one rule and affects only inputs that currently throw.

Validation:
Add a unit case asserting zero diagnostics for the self-referential and mutual-cycle forms, plus the existing single-hop alias case to prove the fix does not regress alias resolution.

Effort: Small: one function and one test.

Risk of the proposed change: Low: the new branch is reachable only on inputs that currently throw.

Dependencies: Not applicable: no prerequisite work.

Open questions: Not applicable: the behavior and the fix are both established.

## [COR-011] Per-file rule state declared in `createOnce` is never reset in `before()`

Record type: Defect or risk
ID category: COR
Primary component: Rule instance lifecycle
Identity statement: Per-file rule state declared in createOnce is not reset in before, so it persists across every file in one lint process
Fingerprint: sha256:197444b8b8d60ba68e870e3b0a54fc82c71efaf10eaa5a3ea5892a49501452ec
Status: Active

Classification: Confirmed defect
Severity or priority: High
Confidence: Confirmed
Affected components: `require-query-before-next` and `validate-gliderecord-calls` produce wrong output; `no-br-current-update` retains a previous file's AST node

Evidence:
- `src/rules/require-query-before-next.ts:23`: `const reported = new Set<number>();` is declared in the `createOnce` closure and consulted at `:33`. The `before()` hook at `:25-28` gates on script context and never clears it.
- `src/rules/validate-gliderecord-calls.ts:37`: the same shape with `reportedMissingQuery`.
- `src/rules/no-br-current-update.ts:24`: `let canonicalCurrent: ESTree.Node | null = null;` is never cleared in `before()` at `:26-29`, and the `Program` visitor returns early at `:32` for a non-full-script file, leaving the previous file's node reachable.
- `plans/002-fix-script-classification.md:117` states the repository's own contract, that `createOnce` runs once per process and per-file state must be reset in `before()`.
- Reproduction with one `createOnce` call and two files, each `var gr = new GlideRecord("incident");` followed by `while (gr.next()) {}` at identical byte offsets, gives per-file report counts of one then zero for both `require-query-before-next` and `validate-gliderecord-calls`. Two control rules report zero for both files, so the pattern is specific to these rules.

Current behavior:
The first file with a violation at a given byte offset is reported. Every later file in the same process whose violation lands at the same offset is silently clean.

Expected or preferred behavior:
Each file is analyzed independently. Byte offsets from one file must not suppress diagnostics in another.

Trigger or scenario:
A single lint process covering more than one file, where two files contain a qualifying violation at the same byte offset. This is common in ServiceNow repositories, where Business Rules and Script Includes are generated from templates and therefore share prefixes and offsets.

Impact:
A false negative in an error-level rule of the `recommended` preset. The user sees a clean result for real defects, which is worse than a false positive because nothing signals that anything was suppressed.

Reach:
Every multi-file lint run using `require-query-before-next` or `validate-gliderecord-calls`.

Root cause:
`createOnce` builds the visitor object once per process, so any closure variable is process-scoped. These sets were written as if the closure were per file.

Why existing tests did not catch it:
`src/runtime/apply-rules.ts:172` calls `createOnce` on every `applyRules` invocation, and `tests/helpers/rule-tester.ts:54-58` calls `applyRules` once per assertion. The harness therefore constructs a fresh closure for every test case and can never observe process-scoped state. Test files additionally run in separate processes, so no test at any level exercises this path.

Minimal reproduction:
Call `createOnce` once, then run the visitor over two parsed files that both contain `var gr = new GlideRecord("incident");` and `while (gr.next()) {}`, and count reports per file.

Recommended action:
Delete both `reported` sets and set `canonicalCurrent` to `null` in `before()`. The analyzer already de-duplicates internally at `src/analysis/query-before-next.ts:27` and `:47-53`, so the rule-level sets are redundant as well as harmful.

Alternative approaches:
1. Clear each set at the start of `before()`. Preserves the existing structure and is the smallest possible edit, but keeps a redundant layer that invites the same mistake again.
2. Delete the sets and rely on the analyzer's own de-duplication. Removes the duplicate mechanism entirely.
3. Keep current behavior. Not applicable: the behavior drops real diagnostics.

Preferred option:
Delete the sets, and separately reset `canonicalCurrent` in `before()` because that value has no analyzer-level equivalent. Confidence is Confirmed. A prerequisite is COR-016, because the analyzer de-duplication those rules would now rely on is itself keyed on offsets.

Implementation outline:
Remove the two set declarations and their guards, add one assignment in `no-br-current-update`'s `before()`, and add a harness that constructs each rule once and replays several files so this class is testable at all.

Compatibility and migration: Not applicable: the change only restores diagnostics that should already be emitted.

Validation:
Add a test-level harness that calls `createOnce` once and lints at least two files, then assert per-file diagnostic counts. Apply it across the rule registry so any future rule with unreset state fails.

Effort: Small: three rule edits. Medium including the new multi-file harness.

Risk of the proposed change: Low: strictly more diagnostics, all of them ones the rules already intend to emit.

Dependencies:
COR-016 should land alongside it so offset-keyed de-duplication is not the only remaining guard.

Open questions:
Whether the real oxlint host reuses one `SourceCode` object across files. It does not affect this finding's conclusion, but it determines whether the per-file analysis cache at `src/analysis/file-analysis.ts:69` also grows for the process lifetime.

## [PER-003] The fixed path-analysis budget is exhausted by an ordinary 300-line script

Record type: Defect or risk
ID category: PER
Primary component: Path-sensitive analysis budget sizing
Identity statement: A fixed work budget is charged per live tracked object, so ordinary-size files exhaust it and silently return partial results
Fingerprint: sha256:b76e46af37f0b4d83044be71c81064a6d3f4ceda6f9380652d6b5ccbb0bd4c13
Status: Active

Classification: Performance risk
Severity or priority: High
Confidence: Confirmed
Affected components: every rule that reads object provenance, which is the majority of the server-side rule set

Evidence:
- `src/analysis/path-state.ts:43`: `const DEFAULT_MAX_WORK = 50_000;` is a constant independent of program size.
- `src/analysis/path-state.ts:279`: `spendWork(budget, 1 + state.env.size + state.objects.size)` charges each state snapshot in proportion to the number of live tracked bindings and objects. Records are not released when a binding goes out of scope, so the per-step cost grows with file length and the total cost grows faster than linearly.
- `src/analysis/path-state.ts:1349-1354`: exhaustion is caught, a counter is incremented, and the partially filled maps are returned.
- Measured with `prefer-glideaggregate` over repeated independent blocks, each a `GlideRecord` construction, a `query()`, a counter, and a `while (gr.next())` loop. 40 blocks at 200 lines give 40 findings with the budget not exceeded. 60 blocks at 300 lines give 47 findings with the budget exceeded once. 90 blocks at 450 lines and 120 blocks at 600 lines both still give 47 findings.
- `src/analysis/path-state.ts:48-54`: the exhaustion counter is exported, and its only readers are `tests/analysis/foundation.test.ts:295` and `tests/rules/cursor-loop-budget.test.ts:58`. Nothing reports it to a user.

Current behavior:
Beyond roughly 300 lines of provenance-bearing code the analyzer stops before finishing and returns whatever it has. The number of findings plateaus and does not grow with file size. No diagnostic, warning, or exit signal indicates the truncation.

Expected or preferred behavior:
An ordinary ServiceNow Script Include should be analyzed completely. If a genuinely pathological file exhausts the budget, the degradation should be observable.

Trigger or scenario:
Any single file with more than roughly 40 to 60 tracked Glide objects. A 300-line Script Include with a few dozen `GlideRecord` locals is entirely ordinary ServiceNow code.

Impact:
Silent false negatives that increase with file size, in exactly the large legacy files where the rules have the most value. Because the plateau is invisible, a user cannot distinguish a clean large file from a truncated one.

Reach:
Every consumer with server-side ServiceNow files above roughly 300 lines.

Root cause:
The budget is a fixed total, but the charging function is proportional to live state, and live state is never pruned. The mechanism was sized for the pathological nested-loop shape that motivated it rather than for ordinary file growth.

Why existing tests did not catch it:
`tests/rules/cursor-loop-budget.test.ts:52-59` asserts only that the counter increments when a synthetic loop spends 100,000 units. `tests/analysis/foundation.test.ts:288-295` has the same shape. No test asserts that findings survive an ordinary large file, and the benchmark corpus fixtures are not asserted for finding counts.

Minimal reproduction:
Lint 60 repetitions of a `GlideRecord` construct, `query()`, counter, and `while (next())` block with `prefer-glideaggregate`, and compare the finding count with the 40-repetition case.

Recommended action:
Make the budget a function of program size, for example a fixed floor plus a per-node allowance, and release object records when their last binding dies so the per-step charge stops growing.

Alternative approaches:
1. Scale `maxWork` with the node count of the program. Smallest change, directly addresses the mismatch between a fixed budget and a size-dependent charge.
2. Prune dead records from the environment at scope exit. Addresses the growth of the charge itself and helps every file, but is a larger change to the state model.
3. Surface exhaustion to the user as a diagnostic or a documented warning. Does not fix the truncation but removes the silence, and is worth doing regardless.
4. Keep current behavior. Not applicable: ordinary files are affected, not pathological ones.

Preferred option:
Option 1 combined with option 3, then option 2 if measurement still shows growth. Scaling the budget restores completeness at realistic sizes immediately; surfacing exhaustion means the next regression is visible rather than silent. Confidence is Confirmed. Evidence that would change the ordering is a profile showing that record retention, not budget size, dominates at 300 lines.

Implementation outline:
Derive the budget in `analyzePathBindings` from a node count computed once per program, keep `runWithTraversalBudget` unchanged for the cursor walkers, and add a per-file flag on `FileAnalysis` recording whether the budget was exhausted so rules or the harness can surface it.

Compatibility and migration: Not applicable: no public contract changes. More diagnostics may appear on large files, which is the intended correction.

Validation:
Add a test that lints a file with several hundred tracked objects and asserts the finding count equals the block count. Add the corresponding fixture to `scripts/benchmark.mjs` so the cost of the larger budget is measured by the existing gate.

Effort: Medium: budget derivation plus a size-scaled regression test.

Risk of the proposed change: Medium: raising the budget raises worst-case analysis time. The existing benchmark gate and the retained ceiling bound the exposure, and POS-004's degradation mechanism remains the backstop.

Dependencies:
Coordinate with REL-004, because a larger budget changes benchmark timings and the current baseline is already unreliable.

Open questions:
What budget multiple keeps the worst-case nested-loop shape from PER-002 inside its current time bound. This needs measurement against the benchmark corpus before a value is chosen.

## [IMP-001] Keep the dependency-free `uses:` matcher and close its remaining evasions

Record type: Improvement or alternative
ID category: IMP
Primary component: Workflow action pin verification
Identity statement: Workflow action references are matched with a regular expression instead of the YAML parser already available in the toolchain
Fingerprint: sha256:d9ad1b6f545501cdf96c393d0a9ae1b5a2e439f26ca7745880136c3b2ff787ff
Status: Active

Classification: Alternative implementation opportunity
Severity or priority: Next
Confidence: Confirmed
Affected components: `scripts/check-action-pins.mjs`, the pre-install `workflow` job, and the compensating structural test

Evidence:
- The hardening recorded for this record landed at commit `4be575e`. `scripts/check-action-pins.mjs:1-3` imports only Node built-ins, `:8-10` uses a `Map` rather than a bare object, `:26-43` tracks block scalars, and `:53-62` makes a reference without an `@`, or with an empty owner or reference, a hard error rather than a silent skip. All of that is verified present.
- The essential property is also intact. `.github/workflows/ci.yml:190-200` runs the check before any dependency install, so a compromised dependency cannot disable it.
- The remaining limitation is now measured rather than theorized. Calling the exported `extractUsesReferences` directly returns an empty list for five legal YAML spellings, namely a folded block scalar, a literal block scalar, an inline flow mapping, a flow sequence of mappings, and a quoted `uses` key. A conventional reference is extracted correctly, so the matcher is not broken, only incomplete.
- The compensating control is real but partial. `tests/release/layer7.test.ts:416-426` re-checks with a real YAML parser and catches those spellings, but it reads only `job.steps[].uses` across the three files in `.github/workflows/`, so job-level reusable-workflow references and any future `.github/actions/**` composite action are outside it.

Current approach:
A line-oriented regular expression extracts `uses:` values, with block-scalar tracking, and compares each against a central pin table. A separate YAML-parsing check in the test suite provides a second opinion.

Why it appears to exist:
The check must run before `npm ci` so that dependency compromise cannot disable pin verification. That constraint rules out the `yaml` package at the point where the check matters most.

What it does well:
The pre-install property is a genuine security control and is rare. The central pin table gives a review-of-record for every action version, and the duplicate-divergence check prevents two workflows drifting apart. The layering instinct, a cheap check early and a thorough check later, is correct.

Actual limitations:
The early check can be bypassed by a workflow edit that uses any of the five spellings, and the late check does not cover every reference site. An attacker who can edit a workflow can therefore introduce an unpinned action that the pre-install gate does not see.

Essential versus accidental complexity:
The pre-install constraint is essential. The incompleteness of the line-oriented matcher is accidental and can be reduced without giving up the constraint.

Triggering context or scale:
Any change that lets a workflow file be modified without the structural test also running, or any addition of a composite action under `.github/actions/`.

### Option A — Keep and harden

Minimal changes: Match any line containing `uses:` first, then reject as malformed any value the reference pattern does not accept, including a block-scalar indicator and a flow-mapping brace. Extend the structural test to job-level `uses` and to `.github/actions/**`.

Benefits: Preserves the pre-install property exactly, closes all five measured evasions by turning them into hard errors, and requires no new dependency.

Costs: The matcher becomes stricter and could reject an unusual but legitimate spelling, which would surface as a build failure rather than a silent pass.

Risks: A false rejection is possible; the mitigation is that the rejection message names the exact line.

Expected lifetime: Indefinite. The check does not need to understand YAML, only to refuse anything it cannot understand.

Correct-use conditions: Appropriate as long as the pre-install property is required, which the current threat model says it is.

### Option B — Incremental redesign

Structural change: Split the check into a strict pre-install syntactic gate that rejects anything non-canonical, and a post-install YAML-parsing gate that runs in the `test` job and covers every reference site.

Benefits: Each half does what it is good at, and the strict early gate becomes easy to reason about because it accepts only one spelling.

Costs: Two checks to maintain, and a project convention that workflows use the canonical form.

Migration steps: Add the strict gate, normalize the existing workflows, then move the structural coverage out of the test file into a named script.

Compatibility considerations: None outside the repository.

Testing requirements: Fixture cases for each rejected spelling, and a case proving the post-install gate sees job-level references.

Rollback strategy: Revert to the single check; the pin table is unchanged either way.

### Option C — Alternative approach

Alternative design: Vendor a minimal YAML subset parser into the script so the pre-install check can parse rather than match.

Benefits: One check, complete coverage, pre-install property retained.

Costs: Vendored parser code to own and audit, which is a poor trade for a file format the project controls.

New risks: A parser bug becomes a security bug in the control itself.

Operational consequences: None beyond maintenance.

Team-skill implications: Owning a parser is a different maintenance burden from owning a matcher.

Dependency implications: No package dependency, but a vendored code dependency.

Migration complexity: Moderate, and it replaces a measured, bounded weakness with an unbounded one.

### Option D — Clean-slate ideal, when useful

Ideal design: Not applicable: the constraint that motivates this design, running before dependency installation, would exist in any clean-slate version, so the ideal design is the same shape as Option A or B.

Incrementally useful parts: Not applicable: no clean-slate design was identified.

Parts not worth pursuing: Not applicable: no clean-slate design was identified.

Rewrite judgment: A rewrite is not justified. The current design is correct in shape and incomplete in detail.

Recommendation: Option A now, Option B if composite actions are introduced. Option A is a bounded edit to one function plus a widening of an existing test, and it converts every measured evasion into a hard error. Confidence is Confirmed. The prerequisite is agreement that a stricter matcher may reject an unusual spelling. Evidence that would change the recommendation is the arrival of `.github/actions/**`, which makes the structural test's file scope the dominant gap and argues for Option B. What must remain untouched is the pre-install execution of this check, which is the property that gives it value.

Expected benefit: Closes a measured bypass in a security control without adding a dependency or weakening the property that makes the control meaningful.

Implementation outline: Reorder the two matches in `extractUsesReferences`, add a malformed-value rejection, extend `tests/release/layer7.test.ts:416-426` to job-level references and to `.github/actions/**`, and add the five spellings as fixture cases.

Compatibility and migration: Not applicable: repository tooling only.

Validation: Assert that each of the five spellings produces a non-zero exit, and that the three current workflows still pass unchanged.

Effort: Small: one function and one test widening.

Risk of the proposed change: Low: the change can only reject more, and every current workflow is verified to pass.

Dependencies: Not applicable: no prerequisite work.

Open questions: Whether the project intends to introduce composite actions. `compositeActionFiles` already scans for them and `.github/actions/` does not exist, so that half of the check is currently dead.

# 10. Security and Privacy Summary

Evidence-based threat model:
This is a developer-tool library with no runtime service, no persisted data, and no user accounts. Three trust boundaries exist. Linted source and its AST are untrusted input to the analyzer. Lint configuration, meaning `settings.servicenow` and rule options, is untrusted input from a repository the plugin does not control. The build and release scripts consume untrusted workflow inputs, tag names, registry responses, and signature bundles. Relaxing any single check converts a chain that fails closed into one that fails open, and the failure would be invisible because a successful publish looks identical either way.

Reuse opportunities:
SEC-001 is the gap in the surrounding governance rather than in this verification. The fail-closed discipline applied here is exactly what the governance audit needs and currently lacks.

## [POS-004] The path-sensitive interpreter degrades under a deterministic budget

Record type: Positive pattern
ID category: POS
Primary component: Path-sensitive analysis budget
Identity statement: The path-sensitive interpreter degrades to unknown facts under a deterministic work and depth budget instead of failing or hanging
Fingerprint: sha256:ee1ad71a309725cf40706db3eb903f878c6645f831afa923bfad5fb43d1c945a
Status: Active

Classification: Positive pattern worth preserving
Severity or priority: Informational
Confidence: Confirmed
Affected components: `src/analysis/path-state.ts` and the two cursor-loop walkers that now run inside the same mechanism

Evidence:
- `src/analysis/path-state.ts:43-45` defines the work budget, the path-depth cap, and the sentinel. `:60-62` charges work and throws the sentinel, `:1141` caps the loop fixpoint at 16 iterations, and `:1349-1354` catches, counts, and degrades rather than propagating.
- `src/analysis/path-state.ts:71-82` exposes the same mechanism as `runWithTraversalBudget`, and both cursor-loop walkers now use it together with a memo keyed on the node and the cursor set. The previously exponential nested do-while shape now completes in single-digit milliseconds.
- `CONTRIBUTING.md:33` states the invariant that every traversal over user source must be bounded by a deterministic budget.

Why it is valuable:
An analyzer over untrusted source must terminate on adversarial and merely unusual input. Choosing bounded degradation over unbounded work means a pathological file produces fewer facts instead of an unresponsive process, and the bound is deterministic so results are reproducible.

Why the current design is appropriate:
A single shared mechanism, exposed for reuse, is better than per-walker ad hoc caps. The counter makes exhaustion measurable, and the sentinel keeps the degradation path distinct from real errors.

Invariants to preserve:
Every traversal over user source must run inside a budget. Degradation must produce fewer facts rather than wrong facts. The bound must remain deterministic and independent of wall-clock time.

Tests and controls that protect it:
`tests/rules/cursor-loop-budget.test.ts` covers the nested-loop shapes and the exhaustion counter, and `tests/analysis/foundation.test.ts:288-295` covers the deep-nesting case.

Risks of changing it:
Removing the budget reintroduces the exponential shape that motivated it. Raising it without measurement trades a silent miss for a slow run, which is why PER-003 and REL-004 must be sequenced together.

Reuse opportunities:
PER-005 records two traversals that still run outside this mechanism, in the Fluent alias resolver and the aggregate counter analysis, both of which the contributing guide's invariant already covers.

Scope limits:
This is the one place where silent degradation was accepted deliberately, and PER-003 shows the limit of that acceptance. The pattern is bounded work, not silent bounded work; at ordinary file sizes the degradation must not occur at all, and when it does occur it should be observable. The budget shape is correct and its current size is not.

## [POS-005] Lint settings are validated as untrusted input and frozen before use

Record type: Positive pattern
ID category: POS
Primary component: Untrusted configuration validation
Identity statement: Lint settings are validated as untrusted input with unknown keys rejected and the result deep-frozen before any rule reads it
Fingerprint: sha256:57556824f48f4f622eb690350a76499527a3cac92c05ac23ec5aa155afae2fe1
Status: Active

Classification: Positive pattern worth preserving
Severity or priority: Informational
Confidence: Confirmed
Affected components: `src/settings/validate.ts`, `src/settings/freeze.ts`, `src/options/descriptor.ts`, and `src/analysis/provenance.ts`

Evidence:
- `src/settings/validate.ts:325-329` rejects any key not in the descriptor, so a typo fails loudly instead of being silently ignored. Every value is checked against an enumeration or an anchored pattern, and cross-field conflicts are rejected explicitly rather than resolved by precedence.
- `src/settings/freeze.ts:5-18` deep-freezes with a cycle guard and walks own keys through property descriptors, and `src/settings/validate.ts:308-315` freezes the shared empty default so one file cannot mutate what another reads.
- Lookups that could be reached by a name from user source use a `Map` rather than a plain object, with the reason recorded inline at `src/analysis/provenance.ts:39-47`. Option parsing rejects unknown keys and uses an own-property check.
- `tests/settings-freeze.test.ts` covers cyclic input, the shared default, and cache invalidation after mutation, and `tests/context.test.ts:11-149` covers twenty rejection cases.

Why it is valuable:
Lint configuration comes from the repository being linted, which is untrusted. Rejecting unknown keys turns a silently ineffective setting into an actionable error, and deep-freezing removes an entire class of cross-file contamination in a process that lints many files with shared defaults.

Why the current design is appropriate:
One descriptor drives the key set, the defaults, the parsing, the freezing, and the fingerprint, so the validator cannot drift from the type. The conflict checks are explicit, which is why FEAT-002 can count them and reason about retiring them.

Invariants to preserve:
Unknown keys must stay rejected. Validated settings must stay deep-frozen. Lookups keyed by a name that can originate in user source must not resolve through a prototype chain. A shared default must never be mutable.

Tests and controls that protect it:
`tests/settings-freeze.test.ts` and the twenty rejection cases in `tests/context.test.ts`.

Risks of changing it:
Accepting unknown keys would make a mistyped setting silently inert, which for a tool whose failure mode is silence is the worst available outcome. Removing the freeze would let one file's analysis alter another's defaults.

Reuse opportunities:
The prototype-safe lookup discipline is applied in the provenance mapping and the action-pin table but not in `src/fluent/registry.ts:276`, where the manifest registry is a plain object. That path is currently guarded by an anchored version pattern applied before lookup, so it is defence in depth rather than a defect, and it is the natural next place to apply the pattern.

Scope limits:
Rejecting unknown keys is right for a closed configuration schema. It should not be extended to data whose shape is expected to evolve independently, such as the parsed registry responses in the release scripts, which correctly tolerate unknown fields while validating the ones they use.
