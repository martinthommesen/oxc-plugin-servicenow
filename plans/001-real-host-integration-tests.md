## Why this matters

This package's entire pitch is "the same plugin works in oxlint and ESLint 9+" (README.md:8), yet nothing in the repo ever loads it into either host. All 136 tests run through a hand-rolled AST walker (`src/runtime/apply-rules.ts`), whose own docstring admits it is "**not** a substitute for oxlint". `oxlint` and `eslint` are optional peerDependencies and are not even installed as devDependencies, so the plugin-loading path (`definePlugin` + `eslintCompatPlugin` wiring, `jsPlugins` specifier resolution, `meta.schema` validation, the real `createOnce` lifecycle) is completely unverified. The suite can be green while the published package fails on load in both hosts. This plan is the verification baseline that every riskier plan (002–004) relies on to catch regressions in the real execution environment.

## Steps

### Step 1: Make the test glob recursive

In `package.json`, change:

```json
"test": "tsx --test tests/*.test.ts tests/rules/*.test.ts",
```

to:

```json
"test": "tsx --test \"tests/**/*.test.ts\"",
```

The quotes matter — the glob must be expanded by the test runner, not the shell.

**Verify**: `npm test` → all 136 existing tests still pass, count unchanged.

### Step 2: Install oxlint and eslint as devDependencies

```bash
npm install -D oxlint eslint
```

Then check which versions resolved: `npm ls oxlint eslint`. The installed oxlint must be a version whose JS-plugin runtime matches `@oxlint/plugins@^1.79.0` (in practice: a current oxlint 1.x). Pin exact versions in `package.json` (no caret) for oxlint — the JS-plugin API is alpha and a floating range invites CI breakage.

**Verify**: `npx oxlint --version` → prints a version; `npx eslint --version` → prints ≥ 9.0.0. `npm run typecheck` → exit 0.

### Step 3: Create bad-code fixtures

Create `tests/integration/fixtures/` with two files that violate known rules:

`tests/integration/fixtures/bad-business-rule.br.js`:

```js
var assignmentGroup = "97c04b3b1b12100043ab85e5bd0713e2";
current.assignment_group = assignmentGroup;
current.u_opened = gs.now();
current.update();
```

Expected rule IDs when linted with the recommended config: `servicenow/no-hardcoded-sysid`, `servicenow/no-gs-now`, `servicenow/no-br-current-update`.

`tests/integration/fixtures/bad-fluent.now.ts`:

```ts
import { BusinessRule } from "@servicenow/sdk";

BusinessRule({
  table: "incident",
  name: "Log state",
});
```

Expected rule IDs: `servicenow/fluent-proper-imports` (wrong module), `servicenow/require-fluent-id` (missing `$id`).

Also create `tests/integration/fixtures/.oxlintrc.json`: copy `examples/.oxlintrc.json` but change the `jsPlugins` specifier to the repo root so oxlint loads the **built** plugin:

```json
{ "name": "servicenow", "specifier": "../../.." }
```

(Resolve relative to the fixtures dir; if oxlint resolves specifiers relative to the config file, `"../../.."` points at the repo root, whose `package.json` `main` is `./dist/index.js` — so `npm run build` must run first. If specifier resolution fails, try an absolute path computed in the test and written to a temp config. If neither works, see STOP conditions.)

**Verify**: files exist; `npm run build` → exit 0 (dist present for the specifier to resolve).

### Step 4: Write the oxlint integration test

Create `tests/integration/oxlint.test.ts`, using `node:test` + `node:assert/strict` (match `tests/filenames.test.ts` style). Shell out with `child_process.execFileSync` (`npx` is not needed — use `node_modules/.bin/oxlint`):

- Run: `oxlint --format json -c tests/integration/fixtures/.oxlintrc.json tests/integration/fixtures/` (check `oxlint --help` for the exact JSON-output flag name in the installed version; it may be `--format=json`).
- Parse stdout JSON. Assert the diagnostics for `bad-business-rule.br.js` include the three expected rule IDs, and `bad-fluent.now.ts` includes the two expected rule IDs.
- Run the same command over `examples/classic-business-rule.js` and `examples/incident-table.now.ts` with the same config and assert **zero** `servicenow/*` diagnostics.
- oxlint exits non-zero when errors are found — pass an options object that tolerates non-zero exit and captures stdout (e.g. wrap in try/catch and read `error.stdout`).

**Verify**: `npm test` → all tests pass including the new oxlint suite. If a specific rule ID is missing from real oxlint output but present in the unit tests, that is a genuine host divergence: record which rule and STOP (see STOP conditions).

### Step 5: Write the ESLint integration test

Create `tests/integration/eslint.test.ts`. Use ESLint's programmatic API in-process (no shelling):

```ts
import { Linter } from "eslint";
import plugin, { configs } from "../../src/index.js";
```

- Instantiate `new Linter({ configType: "flat" })` and call `linter.verify(code, [configs.flat.recommended], { filename })` for the same two bad fixtures (read them from disk) and the two clean examples.
- Assert the same expected rule IDs (ESLint reports them as `servicenow/<rule>`) and zero diagnostics on the clean files.
- Also assert plugin load sanity: `Object.keys(plugin.rules).length === 24` and every rule has a `create` function (the `eslintCompatPlugin` shim).

**Verify**: `npm test` → all pass, including the new ESLint suite.

### Step 6: Fix the examples schema reference

Now that oxlint is installed, `examples/.oxlintrc.json`'s `"$schema": "../node_modules/oxlint/configuration_schema.json"` should resolve. Check the file exists: `ls node_modules/oxlint/configuration_schema.json`. If the installed oxlint ships the schema under a different name/path, update the `$schema` value accordingly; if it ships no schema file, remove the `$schema` line.

**Verify**: `node -e "const fs=require('node:fs'); const path=require('node:path'); const cfg=JSON.parse(fs.readFileSync('examples/.oxlintrc.json','utf8')); if (!cfg['\$schema']) { console.log('schema key removed'); process.exit(0); } const target=path.resolve('examples', cfg['\$schema']); if (!fs.existsSync(target)) { console.error('missing', target); process.exit(1); } console.log(target);"` → prints the resolved schema path (or `schema key removed`) and exits 0.

### Step 7: Wire integration tests into CI

The integration tests need `dist/` built (step 3's specifier). In `.github/workflows/ci.yml`, the `npm run build` step already runs last. Reorder so build runs before tests, or add a dedicated step after build:

```yaml
      - run: npm run build
      - run: npm test
```

(Simplest: move `- run: npm run build` above `- run: npm test`; the recursive glob from step 1 already picks up `tests/integration/`.)

**Verify**: `npm run build && npm test` locally from a clean `dist` (`npm run clean && npm run build && npm test`) → all pass.
